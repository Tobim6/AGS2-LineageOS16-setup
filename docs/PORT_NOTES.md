Building a brand-new LineageOS 16 (Android 9) device tree for the Huawei MediaPad T5, from scratch, using Huawei stock firmware dumps as the blob/kernel source. **This memory supersedes earlier kernel-generation/boot-architecture details from the first session — see the EMUI8 pivot section below, which is the current ground truth.**

**Hardware identity (confirmed from the actual firmware dumps):**
- Internal Huawei codename: **Dallas**
- SoC/board platform: **hi6250** (HiSilicon Kirin 659) — `TARGET_BOARD_PLATFORM := hi6250` was never actually set anywhere in upstream `hi6250-common`; added it to `BoardConfigCommon.mk` (previously `ro.board.platform`/`ro.product.board` resolved empty, `ro.hardware` happened to still work via DTB fallback).
- Retail model codes: user's own physical tablet is **AGS2-W09** (WiFi-only). The original HarmonyOS 2.0 firmware dump used as the initial base is for **AGS2-L09/AL00** (cellular variant) — telephony/modem support kept in the tree deliberately.
- Device has **no anti-rollback protection** (user-confirmed) and testpoint-based hardware recovery is always available regardless of bootloader state — this is the standing safety net used after several bad flashes below.
- Bootloader is **heavily locked down**: rejects standard `fastboot flashing unlock`/`unlock_critical` (the latter is password-gated, no known password). `dd` from inside TWRP writes directly to the block device and bypasses this authorization layer entirely — the only way custom partition content has gotten onto the device at all.
- **AVB/vbmeta — correction (2026-10-20, verified live on-device): the earlier claim that a disabled-verification vbmeta was flashed and still in effect was WRONG.** A direct `dd` read of the live `vbmeta` partition (parsed the AVB header: magic `AVB0`, `flags` field at header offset 120, big-endian) shows **flags = 0x0 — verification and hashtree are both currently enabled**, not disabled. User confirmed this is because a full stock EMUI8 flash was done at some point, which reset vbmeta back to stock. **However, this is confirmed NOT the current boot blocker**: boot demonstrably progresses well past any AVB gate — kernel loads, init runs, and reaches `/data` `mkdir` failures (logged in kernel console), which could not happen if AVB verification were hard-rejecting partition content. Don't re-chase vbmeta/AVB as a cause unless new evidence specifically points there again.
- **Device-identity question resolved**: `adb devices` showing `model:HUAWEI_P8_lite_2017 device:prague` is confirmed to be the right physical device (user-confirmed) — this is just TWRP's own inherited/never-relabeled build identity string, not a wrong-device connection. No longer an open concern.

**MAJOR PIVOT (same day, later session): entire boot chain switched from HarmonyOS 2.0 to EMUI8.** Root driver: HarmonyOS 2.0's bootloader enforces AVB (`hisi_avb`/`load_kernel: avb`) and rejects a custom kernel — confirmed this is **not** disabled-until-EMUI10 as a much earlier guess claimed (that guess was wrong; the AVB strings are near-identical across EMUI8/EMUI9/HMOS2.0 FASTBOOT.img). Tested and failed: swapping only FASTBOOT.img to EMUI9 or EMUI8 → device needed testpoint recovery; swapping XLOADER+FASTBOOT to EMUI8 while keeping HMOS2.0 kernel/system/vendor → booted into full stock EMUI8 (ignored our content entirely). **Conclusion: the whole secure chain (XLOADER/FASTBOOT/TEEOS/TRUSTFIRMWARE) must be internally consistent from one firmware generation — no partial-tier swaps.** EMUI8 (not EMUI9) was chosen specifically because the user's own prior, separate LineageOS 20 project on this same AGS2 device already proved a custom kernel boots on EMUI8's chain, and its AIK-Linux tooling/firmware files are genuine and reused here.
- Kernel source is now **EMUI8** (Linux 4.4.23, "Roaring Lionus"), imported into `kernel_huawei_AGS2` preserving git history — replacing the HarmonyOS 2.0 (4.9.148) baseline from the first session. EMUI9's kernel (also 4.9.148, byte-identical header/offsets to HMOS2.0) was considered and rejected as a backport target — too large a 4.4→4.9 generation gap (binder/ion/cgroups etc. all differ) vs. just using EMUI8 source directly.
- EMUI8's GPL release is actually **more complete** than HarmonyOS 2.0's: real (non-stubbed) D5500 Imagination video-codec platform glue exists, and complete DTS auto-generate tooling (670 files, includes a real `agassi2` overlay) exists — meaning a real from-source DTB is now possible. Neither opportunity has been acted on yet (D5500 config left enabled only; DTS tooling not yet used, still relying on stock DTS.img).
- Defconfig deltas reapplied for EMUI8's Kconfig: `-fcommon` HOSTCFLAGS fix, `CONFIG_LOCALVERSION="-lineage"` + `CONFIG_LOCALVERSION_AUTO=y`, `# CONFIG_TYPEC_CAP_CUSTOM_SRC2 is not set`. (Old HMOS2.0-era deltas for TCP_NODELAY/HISHOW/EROFS_FS/DM_SNAPSHOT don't apply to 4.4's Kconfig.)
- **Critical kernel config fix**: EMUI8 stock defconfig has both `CONFIG_SECURITY_SELINUX_BOOTPARAM` and `CONFIG_SECURITY_SELINUX_DEVELOP` unset, so `security_setenforce()` for the `androidboot.selinux=permissive` cmdline hard-rejects with EINVAL, crashing the kernel and forcing a reboot to bootloader — this crash was being misread as a bootloader-level "BOOT IMAGE LOAD FAIL", not a kernel panic. Setting both `=y` is what got the new kernel booting into recovery for the first time.

**Boot architecture: EMUI8 is ramdisk-based, not System-As-Root — a real structural difference from HarmonyOS 2.0/EMUI9.** HMOS2.0 and EMUI9 (byte-identical kernel header offsets to each other) both use SAR with a genuinely empty ramdisk on the ramdisk-less `KERNEL` partition; EMUI8 pairs that same ramdisk-less `KERNEL` partition with a separate, real, populated gzip-cpio `RAMDISK` partition (confirmed via AIK unpack of stock RAMDISK.img: real `/init`, `init.rc`, 17.7MB). The SAR→ramdisk convention switch happens specifically between EMUI8 and EMUI9.
- Device tree changes: `BOARD_BUILD_SYSTEM_ROOT_IMAGE := false` (was `true`); `BOARD_MKBOOTIMG_ARGS` ramdisk_offset is now EMUI8-specific `0x07b88000` (was `0x0ff88000` for HMOS2.0/EMUI9 — **this supersedes the HMOS2.0 offset documented in the original "Resolved via AIK-Linux" milestone below**). `kernel_offset`/`second_offset`/`tags_offset` and `BOARD_KERNEL_BASE 0x00478000` are confirmed byte-identical across all three firmware generations via AIK, so those are unchanged.
- `mka bacon`'s single combined `boot.img` (kernel+ramdisk) is wrong for this device's two-partition (KERNEL + RAMDISK) layout — the OTA `updater-script` needed a fix to additionally extract/flash a split ramdisk file to the ramdisk partition. This got superseded later in the session by flashing loose partition images directly and skipping the OTA zip entirely (see workflow note below).
- **Working image-build method, per explicit user instruction — do not deviate:** AIK-Linux unpack the *original stock EMUI8* `KERNEL.img`, swap in only the compiled `Image.gz`, repack keeping the stock header (base/offsets) untouched. For the ramdisk: AIK-unpack stock `RAMDISK.img` and **replace the contents of the extracted `ramdisk/` directory** — AIK always repacks from that directory tree, never from a file dropped elsewhere (a real bug hit once). A raw/unwrapped `ramdisk.img` (no bootimg header) flashed directly was tried once and booted *worse* (immediate error screen) with a byte-identical kernel — confirms the ramdisk-wrapping step is required, not optional.
- **Workflow note for future sessions:** loose partition images (`KERNEL-emui8-*.img`, `RAMDISK-emui8-*.img`, `VENDOR-emui8-*.img`, etc.) are flashed directly via fastboot/dd by the user. **Do not rebuild/reflash the whole OTA zip for every fix** — that was explicitly flagged as wasteful.
- The kernel **cmdline is a header string, not baked into the kernel binary** — editable via a pure AIK unpack/edit-cmdline/repack with no kernel rebuild needed. Used to bump `loglevel=4`→`8` for full console verbosity, which is what eventually surfaced the real `/data` root cause below.

**fs_mgr / init bugs found and fixed (patched directly in the repo-synced `lineage-16.0` tree, which has no git/worktree — edited in place):**
- `fs_mgr_do_mount_one()` (first-stage init's mount path) was missing the raw-partition-type skip (`"swap"/"emmc"/"mtd"`) that sibling `fs_mgr_do_mount()` already had — added it. Fixes DT fstab entries `bfi`/`dfx`/`misc`/`rrecord` (Huawei's type="emmc" "don't really mount" sentinel) that were hard-failing boot with ENODEV.
- **Bigger root cause**: this device's DT fstab `dev` values for every real filesystem entry are a bare, unresolvable placeholder literal `/by-name/<partition>` — not a real path, and not even the by-name symlink convention a naive fix assumes (that symlink only gets built when a `boot_devices` DT property matches, which this DTB lacks). This device is also `VBootV1` (DT uses `vbmeta_hisi`/`vbmeta_huawei`, not plain `vbmeta`), not `VBootV2`. Fix: promoted the by-name symlink map (previously only built for `FirstStageMountVBootV2`) into the shared base class, added `ResolveDtByNamePlaceholders()` called just before `MountPartitions()` to substitute each placeholder for the real runtime-queried symlink.
- `MountPartitions()` aborted boot on ANY mount failure — added `IsMountPointEssential()` (only `/system`,`/vendor`,`/odm`,`/product` are fatal). Everything else (bfi, cust — genuinely has no valid filesystem/stock image on this hardware, safe to ignore — dfx, misc, patch_hw, preas, preavs, ramdisk, rrecord, version) now warns and continues instead of hanging boot.
- `mount_all /vendor/etc/fstab.${ro.hardware}` was **never called at all** in the LineageOS-rewritten `init.hi6250.rc`'s `on fs` block (genuine stock EMUI8 init.rc calls it as the very first `on fs` action) — meaning `/data`,`/cache`,`/sec_storage`,`/misc` were never reaching vold's second-stage mount regardless of any other fix. Added the call back in.
- 8 more `wait`-flagged raw mounts in `init.hi6250.rc` (cust/preload/product/version ×2 slot variants) also used the bare unresolvable `/by-name/X` path, each blocking ~20s on timeout and stacking sequentially — a real contributor to long/inconsistent boot-hang timing. Fixed to the confirmed-real `/dev/block/bootdevice/by-name/X` prefix.

**Root cause of "/data never initializes" (chased through several real-but-secondary bugs above as red herrings, including the stale init.hi6250.rc delay):** with kernel loglevel bumped to 8, found **direct log evidence** that `/data` mounts successfully but **read-only** — every single `/data/*` `mkdir` in `on post-fs-data` fails with the explicit kernel-logged error `mkdir() failed: Read-only file system` (e.g. `/data/bootchart`, `/data/system`), not ENOENT — which is what was producing the separate-looking zygote/keystore/gatekeeper "No such file or directory" symptoms. This is the same investigation documented in the TWRP/f2fs section below (modern `mkfs.f2fs` superblock features the EMUI8 f2fs driver doesn't understand → defensive RO mount) — fixed via `-O encrypt` reformat, superblock going from `features=481: encrypt verity quota_ino` to `features=1: encrypt`, confirmed clean via fsck afterward. **The device still did not boot after this fix, and the session ended before a clean post-fix boot log was captured** (the pstore-pulling that followed got confused re-verifying old/corrupted dumps instead of gathering fresh ones) — see open questions below. The f2fs fix was a `mkfs.f2fs -O encrypt` run directly on the device's `/data` partition via adb/TWRP shell, not an image flash — it has no corresponding deliverable file.

**Key technical gotcha — legacy EROFS "VLE" format (HarmonyOS 2.0 dump only, not relevant to the current EMUI8-based boot chain but still used for HMOS2.0 vendor/product/odm blob extraction):** the HMOS2.0 system/vendor/product/odm images use Huawei's original 2017-2018 `drivers/staging/erofs` on-disk format (`CONFIG_EROFS_FS_HUAWEI_EXTENSION`), structurally different from modern mainline z_erofs — no desktop tooling can read compressed file content from these images (directory/metadata parsing works fine; only z_erofs-compressed regular files fail). Plain LZ4 codec, not a compression-algorithm issue.
**Built a working standalone userspace decoder**: `/home/tobim6/AGS2_LOS16/work/tools/vle_extract.py`, transcribed directly from the GPL kernel source's `fs/erofs/{erofs_fs.h,inode.c,unzip_vle.c,unzip_vle_lz4.c,unzip_lz4.c,internal.h}`, reimplementing `z_erofs_map_blocks_iter` + `vle_get_logical_extent_head`'s backward-chaining cluster resolution plus standard LZ4 decompress via `liblz4`. Two subtleties: (1) the decompressed buffer's byte 0 corresponds exactly to resolved file offset `la`, never `la mod clustersize`; (2) must call `LZ4_decompress_safe_partial(src, dst, srcSize, targetOutputSize=llen, dstCapacity=llen+slack)`, not plain `LZ4_decompress_safe`, matching the kernel's own `__lz4_decompress_safe_partial`. Validated byte-perfect against real files (ELF `readelf -a`, correct BuildIDs; readable XML). A small residual of blocks use a newer on-disk variant not in this GPL snapshot and are unextractable by any means — logged to `<partition>_batch_fail.log` rather than crashing.
Supporting tools in `/home/tobim6/AGS2_LOS16/work/`: `erofs-utils` v1.9.4 (needs `CFLAGS="-fcommon -Wno-error"` on this machine's GCC) for directory/NID resolution; `tools/batch_extract.py` fills extraction gaps via `vle_extract.py` + `dump.erofs --path`.

**SUPERSEDES the f2fs-superblock theory as "the" root cause — REAL root cause found (2026-10-20, log-verified, not guessed): `/dev/block/bootdevice` is a broken/dangling symlink on this device, because `${ro.boot.boot_devices}` is never set anywhere.** Checked and ruled out as the source for this property: the kernel cmdline (both our current build and genuine stock EMUI8's own `KERNEL.img`, unpacked via AIK — neither has `androidboot.boot_devices=`), and the live DTB (`/proc/device-tree/firmware/android/` has no `boot_devices` node at all, only `fstab/{bfi,dfx,odm,cust,misc,system,vendor,product,version,...}`, `vbmeta_hisi`, `vbmeta_huawei`, `name`, `compatible`). `hi6250-common`'s `rootdir/etc/init.hi6250.rc` does `on init: symlink /dev/block/platform/${ro.boot.boot_devices} /dev/block/bootdevice`, which with an empty substitution points at the wrong location — so `/dev/block/bootdevice/by-name/<X>` never resolves for ANY partition. Confirmed via fs_mgr source (`fs_mgr.cpp`, the `LERROR << "Skipping '" << ... << "' during mount_all"` branch fires specifically when an `MF_WAIT` entry's block device fails `fs_mgr_wait_for_file()` within 20s) and via the actual boot log showing exactly this skip for **all three** `/dev/block/bootdevice/by-name/*`-based fstab entries that reach `mount_all` (`userdata`, `cache`, `splash2`) — not an isolated `/data`-only problem. ## Build pitfalls found while turning the hand-patched live system into a clean OTA
- **Stale `out/`**: images are packed from whatever is in `out/target/product/AGS2/{system,vendor}`. Old leftovers (e.g. an old `init.tee.rc`, a
  standalone camera provider, HMOS libs) were silently shipped. Run `make installclean` before the final `mka bacon`.
- **Old mtimes**: firmware blobs carry 2021 mtimes, so make never re-copies a changed blob over an older `obj/` intermediate. Mirror the vendor
  repo with `scripts/sync_vendor.sh` (no mtime preservation) or `touch` the files after copying.
- **Dropped modules** (commit b0f5ee2) removed keymaster/gatekeeper/allocator/composer/health/bluetooth/memtrack/thermal/usb/drm services whose names
  collide with AOSP; they are re-added as `<name>_emui8` modules (same stem). Same trick for libs; strip `.gnu_debugdata` from such blobs
  (`objcopy --remove-section .gnu_debugdata`) or the AOSP twin's strip step fails.
- **rc files** must install to `/vendor/etc/init` (`LOCAL_PROPRIETARY_MODULE` + `LOCAL_MODULE_RELATIVE_PATH := init`), not `/system/etc`.
- **TEE**: `system_teecd`, `libtuidaemon`, both `native_packages.xml` must be packaged, otherwise every TEE session fails (keymaster/gatekeeper crash-loop
  -> endless boot animation).
- `tools/check_image.py <PRODUCT_OUT> <known-good dmesg>` checks DT_NEEDED closure and that every service of a known-good boot is defined.
- The OTA must not contain `compatibility.zip` (hi6250-common releasetools.py disables it).
